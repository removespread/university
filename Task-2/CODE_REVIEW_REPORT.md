## 1. Резюме

Проект аккуратно структурирован, разделён на `backend`/`frontend`, снабжён
осмысленными JSDoc-комментариями, документацией (README) и интеграционными
тестами. Код читается легко, соблюдён единый стиль, используется единый формат
ошибок API. Это хороший уровень для учебного проекта.

Вместе с тем выявлен ряд **существенных проблем безопасности** (в первую очередь
отсутствие проверки прав доступа к ресурсам и небезопасные значения секретов по
умолчанию), а также замечания по архитектуре, обработке ошибок и покрытию
тестами. Ниже они сгруппированы по категориям с указанием серьёзности.

**Итоговая оценка:** проект работоспособен и пригоден для демонстрации MVP, но
**не готов к production** до устранения проблем безопасности категории 🔴.

## 2. Оценка по критериям

### 2.1. Структура проекта — 👍 хорошо

- Чёткое разделение `backend`/`frontend`, слои `models`/`controllers`/`routes`/`middleware`.
- Точка входа (`server.js`) отделена от конфигурации приложения (`app.js`) — это
  правильное решение, упрощающее тестирование через Supertest.
- Именование файлов и каталогов последовательное и предсказуемое.

### 2.2. Документация — 👍 хорошо

- `README.md` подробный: описание, стек, структура, инструкции запуска, полная
  таблица REST API, примеры `curl`, формат ошибок.
- Код снабжён JSDoc-комментариями на русском языке, соответствующими ТЗ (ссылки
  на FR/NFR).
- **Замечание:** нет раздела о модели прав доступа (кто и что может делать) —
  это напрямую связано с проблемой безопасности F1.

### 2.3. Соответствие стандартам кодирования — 👍 в целом хорошо

- Единый стиль, `'use strict'`, единый формат ответов об ошибках.
- **Замечание:** в проекте нет линтера (ESLint) и форматтера (Prettier), хотя в
  коде присутствуют директивы `// eslint-disable-next-line`. Конфигурация ESLint
  отсутствует — директивы ни на что не влияют.

### 2.4. Архитектура и организация кода — 🟡 есть замечания

- **F5.** Валидация `priority`/`status` продублирована в `createTask` и
  `updateTask` (см. [`taskController.js`](Task-2/backend/src/controllers/taskController.js:40)).
- **F5.** Поиск задачи `Task.findOne({ where: { id, projectId } })` повторяется в
  трёх методах — просится вынос в хелпер.
- **F5.** Функция [`findProjectOr404()`](Task-2/backend/src/controllers/taskController.js:15)
  названа так, будто возвращает 404, но фактически это просто `Project.findByPk`.
  Имя вводит в заблуждение.
- Бизнес-валидация целиком в контроллерах; для роста проекта стоит выделить слой
  валидации (например, `express-validator` или Joi) и/или сервисный слой.

### 2.5. Обработка ошибок — 🟠 есть серьёзное замечание

- 👍 Централизованный [`errorHandler`](Task-2/backend/src/middleware/errorHandler.js:22)
  с единым форматом и обработкой ошибок Sequelize — хорошее решение.
- **F4.** В [`app.js`](Task-2/backend/src/app.js:44) модуль `authRoutes`
  подключается через `try/catch`, который **молча проглатывает любую ошибку**, а
  не только «модуль не найден». Если в `authController` появится синтаксическая
  ошибка или упадёт `require`, аутентификация просто «тихо исчезнет», и отладка
  станет крайне трудной. Это антипаттерн.

### 2.6. Безопасность — 🔴 критические замечания

- **F1 (Critical). Broken Access Control / IDOR.** Маршруты проектов и задач
  используют `optionalAuthenticate`, то есть **работают вообще без токена**. Любой
  анонимный пользователь может прочитать, изменить или удалить любой проект и
  любую задачу по ID. Проверки `ownerId` нигде нет. Это самый серьёзный дефект.
- **F3 (Critical).** [`getProjects()`](Task-2/backend/src/controllers/projectController.js:44)
  делает `Project.findAll()` без фильтра — возвращает проекты **всех**
  пользователей. Утечка чужих данных.
- **F2 (Critical). Секреты по умолчанию.** `JWT_SECRET` откатывается к строке
  `'change_me_in_production'` сразу в трёх местах (authController, middleware,
  .env.example, docker-compose). Если переменную забудут задать в production,
  токены можно будет подделать. Реальные пароли БД (`secure_password`) захардкожены
  в [`docker-compose.yml`](Task-2/docker-compose.yml:23).
- **F6 (Minor).** `express.json()` вызывается без опции `limit` — потенциальный
  вектор DoS большими телами. CORS по умолчанию открывается на `*`.
- 👍 Пароли хешируются `bcrypt` (10 раундов), хеш не утекает наружу
  (`toPublicJSON`), при логине не раскрывается, что именно неверно — это сделано
  правильно.

### 2.7. Производительность — 🟡 некритичные замечания

- **F7.** Списки проектов и задач возвращаются целиком, без пагинации/лимита. На
  больших объёмах это проблема.
- **Frontend.** После каждого создания/удаления выполняется полная перезагрузка
  списка (`loadProject`/`loadProjects`) — приемлемо для MVP, но неоптимально;
  можно обновлять состояние локально.
- `getProjects` не подгружает счётчик задач, из-за чего UI не может показать
  прогресс без дополнительных запросов.

### 2.8. Читаемость и поддерживаемость — 👍 хорошо

- Код понятный, комментарии по делу, компоненты небольшие.
- **Замечание:** магические литералы (`'#3498db'`, статусы, приоритеты) частично
  вынесены (в модели `Task`), но дефолтный цвет и ключи `localStorage`
  дублируются — стоит централизовать константы.

### 2.9. Тестирование — 🟡 есть замечания

- 👍 Есть интеграционные тесты на health, создание проекта, валидацию, создание и
  получение задач, полный флоу аутентификации.
- **F8.** Не покрыты: обновление/удаление/завершение задачи, фильтрация по
  `status`/`priority`, ветки `404` для несуществующих проектов/задач, отклонение
  недопустимого приоритета/статуса. Нет тестов фронтенда.
