# Стратегия тестирования TaskFlow

## 1. Цель

Обеспечить корректность, надёжность и соответствие функциональным требованиям
(FR-1…FR-4) backend приложения TaskFlow с помощью автоматизированных тестов и
достичь покрытия кода не менее **70%**.

## 2. Объект тестирования

REST API TaskFlow (`Task-2/backend`): Node.js + Express + Sequelize (SQLite/PostgreSQL).

Тестируемые модули:

| Слой         | Модули                                                        |
| ------------ | ------------------------------------------------------------ |
| Модели       | `User`, `Project`, `Task` (валидация, значения по умолчанию, методы) |
| Контроллеры  | `authController`, `projectController`, `taskController`      |
| Middleware   | `auth` (JWT), `errorHandler`                                 |
| Конфигурация | `config/env` (fail-fast для JWT_SECRET)                      |
| Маршруты     | `authRoutes`, `projectRoutes`                                |

## 3. Виды тестирования

### 3.1. Модульное тестирование (Unit)

Изолированная проверка отдельных функций и модулей.

- **Модели** — значения по умолчанию, валидация полей (`notEmpty`, `isEmail`),
  методы `User.setPassword` / `verifyPassword` / `toPublicJSON`, справочники
  `Task.PRIORITIES` / `Task.STATUSES`.
- **Middleware** — логика `authenticate` / `optionalAuthenticate` и обработчиков
  ошибок проверяется с использованием **моков** объектов `req` / `res` / `next`
  (без поднятия HTTP-сервера).
- **Конфигурация** — fail-fast логика JWT-секрета в разных `NODE_ENV`
  (используется `jest.isolateModules` для перезагрузки модуля с разным окружением).

### 3.2. Интеграционное тестирование (Integration)

Проверка взаимодействия компонентов через полный HTTP-цикл с помощью **Supertest**:
маршрут → middleware → контроллер → модель → БД → ответ.

- CRUD проектов и задач;
- фильтрация задач по статусу и приоритету;
- регистрация/вход/JWT-аутентификация;
- взаимодействие с БД (in-memory SQLite);
- сквозная связка `auth ↔ projects` (привязка `ownerId` к пользователю по токену).

### 3.3. Функциональное тестирование

Реализуется в рамках интеграционных тестов: каждый функциональный сценарий из ТЗ
(создание проекта, добавление задачи, отметка выполнения, вход пользователя)
покрыт end-to-end проверкой ожидаемого поведения API.

### 3.4. Регрессионное тестирование

Весь набор (`npm test`) запускается при каждом изменении кода. Пороговое покрытие
в `coverageThreshold` не даёт «просесть» качеству: сборка падает при покрытии
ниже 70%. Тесты, добавленные по итогам код-ревью (F8), фиксируют ранее исправленные
дефекты и предотвращают их повторное появление.

### 3.5. Нагрузочное тестирование (опционально)

В объём текущей работы не входит. Для будущего развития рекомендуется `autocannon`
или `k6` для проверки NFR по производительности (время ответа API).

## 4. Подход к тестовым данным и изоляции

- **In-memory SQLite** (`DB_STORAGE=:memory:`) — быстрая, полностью изолированная
  БД; не требует внешней СУБД и не оставляет артефактов на диске.
- Перед каждым набором интеграционных тестов схема пересоздаётся
  (`sequelize.sync({ force: true })`).
- Моки (`jest.fn`, ручные объекты `req/res`) применяются для изоляции unit-тестов
  middleware от Express.
- Переменные окружения задаются централизованно в `tests/setup/env.js` до загрузки
  тестируемого кода.

## 5. Критерии приёмки

| Критерий                              | Значение         |
| ------------------------------------- | ---------------- |
| Все тесты проходят                    | 100% (0 падений) |
| Покрытие строк / операторов           | ≥ 70%            |
| Покрытие ветвей                       | ≥ 70%            |
| Покрытие функций                      | ≥ 70%            |
| Позитивные сценарии                   | покрыты          |
| Обработка ошибок и граничные условия  | покрыты          |

## 6. Инструменты

- **Jest** — тест-раннер и измерение покрытия (провайдер V8).
- **Supertest** — HTTP-клиент для интеграционных тестов.
- **Отчёты покрытия** — `text`, `text-summary`, `lcov`, `html`.

## 7. Запуск

```bash
cd Task-3
npm install
npm run test:coverage
```
